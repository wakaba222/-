## 2. 実装Phase (仕様43章準拠)

| Phase | 内容 | 完了条件 |
|---|---|---|
| **0** | 本設計レビュー・確定 | ✅ 完了 |
| **1** ✅ | プロジェクト初期化 / Supabaseスキーマ / RLS / Auth / ロール振り分け | ADMIN・COACHでログインでき、他人のデータが**DBレベルで**見えない |
| **2** ✅ | 顧客・コーチ管理 / 目標設定・承認フロー / 担当履歴 | 顧客登録→目標設定→ADMIN承認 が通る |
| **3** ✅ | 成果登録 (スマホUI・即時達成判定・履歴保持) | 成果登録で完全達成が自動判定される |
| **4** ✅ | 売上登録 / 商品マスタ / 取消・返金 / SNS区分 | 売上登録でインセンが表示される |
| **5** ✅ | **評価エンジン** (純粋関数 + ルールJSON + スナップショット) | 仕様35章のテスト13件が全て通る |
| **6** ✅ | Coach Dashboard | 「現在地」と「次の条件」が1画面で分かる |
| **7** ✅ | Admin Dashboard / CSV出力 | 全コーチ比較・並替・絞込 |
| **8** ✅ | 昇格判定 / 四半期ボーナス / 月次締めジョブ / 通知 | 昇格候補が自動抽出される |
| **9** ✅ | テスト拡充 (異常系・境界値) | 仕様36章の異常系を網羅 |
| **10** ✅ | UI polish (高級感・白+ダークグリーン+ゴールド) / レスポンシブ最終調整 | スマホ実機で成果登録10秒 |

Phase 5 を先に完成させ、**Phase 6/7 は「エンジンの出力を並べるだけ」**にした。
seedデータ (ADMIN1・コーチ3・顧客27・昇格候補1名) は Phase 2 の時点で投入済みで、常にデモ可能な状態を保っている。

### 実装状況 (2026-08 時点)

全Phaseを実装済み。検証結果は以下のとおり。

| 検証 | 手段 | 結果 |
|---|---|---|
| 評価ロジック | `npm test` (Vitest 60件) | 仕様35章の必須13ケース + 36章の異常系すべて通過 |
| 型・Lint・ビルド | `npm run typecheck` / `lint` / `build` | エラー0・警告0 |
| RLS | `npm run db:local` (psql) | COACHが他コーチの顧客・売上へ到達不能。監査ログに変更前後が記録される |
| DB→評価→昇格 の通し | `npm run verify:seed` | 田中=昇格候補(108.5) / 鈴木=最高評価(120) / 佐藤=基準未達(50.2) |

未実施なのは Supabase 実環境 (Auth・PostgREST) への接続確認のみ。
ローカルは PostgreSQL 直結でスキーマ・RLS・評価まで検証している。

## 3. 技術的リスクと対策

| # | リスク | 影響 | 対策 |
|---|---|---|---|
| R1 | **RLSの再帰参照** (coachesを見るためにcoachesを見る) でポリシーが無限再帰 | Phase 1 が止まる | `SECURITY DEFINER` 関数 `auth.is_admin()` / `auth.coach_id()` に切り出し、ポリシーからは関数のみ参照 |
| R2 | **月末・タイムゾーン境界** のズレ (UTC保存/JST判定) で「4ヶ月目」の判定が1日ズレる | 評価が不正確 | 日付境界ユーティリティをJST固定で1箇所に集約。境界値テスト(月末日・うるう年・31日始まり)を必須化 |
| R3 | **経過月数の定義** (1/31開始 → 5/31 or 5/30?) | 対象判定のブレ | 「開始日の同日 or 月末丸め」を明文化し、`elapsedMonths` にテストを書く |
| R4 | **スナップショットの再計算と不変性の衝突** (返金・成果訂正が過去月に波及) | 過去評価が変わる/変わらない の混乱 | `revision` 方式。旧revisionは残し、確定ボーナスは「支給済みフラグ」で凍結。差分はADMIN画面に警告表示 |
| R5 | Supabase プロジェクトの実接続情報が未提供 | DB作業が検証できない | ローカルは docker + Postgres でマイグレーション検証。評価ロジックはDB非依存のためテストは常に実行可能。接続情報は後から `.env` 差し替えのみ |
| R6 | 評価対象0人・分母0 のケースが全画面に波及 | 表示崩れ・NaN | ドメイン層で `null` を返し、UIは `N/A` 表示を型で強制 (`number \| null` を許容する専用コンポーネント) |
| R7 | 商品価格・インセン額の後日変更が過去に波及 | 支給額の齟齬 | `sales` に成約時点の値をコピー保存 (スナップショット化) |
| R8 | 「120点上限」と補間の外挿 | 想定外の高得点 | 全配点関数で `clamp(0, max)` を強制。プロパティテストで上限超過が出ないことを検証 |
| R9 | 制度変更時に過去評価が再計算される事故 | 信頼性の致命傷 | スナップショットは `rules_version` 必須。再計算APIは「対象月を明示指定」しないと動かない |

## 4. MVPで削る / 後回しにするもの (提案)

**削る (DB設計だけ用意し、機能は作らない)**
- SNS経由新規獲得インセンティブの計算 (記録のみ)
- Instagram / YouTube / 講義 / イベント の定量自動集計 → P3/P4はADMINチェックボックスで代替
- 顧客本人向け成果画面
- 外部連携全般 (Robot Payment / Google Calendar / LINE / Slack)
- コーチ別LTV・商品別利益率・AI改善提案

**簡素化する**
- 通知 (仕様41章) → **メール/LINEは実装せず、アプリ内通知 + ダッシュボードのアラート帯のみ**。
  月次ジョブで「4ヶ月目到達」「90%まであと1名」「60日以上未更新」「昇格候補」を生成
- グラフ → Score推移(6ヶ月)と売上推移(12ヶ月)の2種のみ
- 給与シミュレーション → レッスン数は月1回の手入力。実給与システムとは完全分離の「参考値」表示
- CSV出力 → コーチ一覧・売上明細・顧客一覧の3種のみ

**絶対に削らないもの (MVPの核)**
評価エンジン / スナップショット / ルールversion管理 / RLS / 監査ログ / コーチダッシュボードの「次に何をすべきか」表示。
