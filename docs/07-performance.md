# 07. パフォーマンス監査と改善

対象: 本番 `https://flame-eight-54.vercel.app`
方針: **評価仕様・RLS・監査ログ・snapshot の正確性は一切変えない。取得方法と配置だけを変える。**

---

## 1. 計測方法

推測で直す前に、何が遅いかを数字で押さえた。

| 何を | どうやって |
|---|---|
| TTFB (最初のバイトまで) | 本番URLへ `curl -w %{time_starttransfer}` を各画面5回、中央値を採用 |
| Supabase への問い合わせ本数・各所要時間 | `src/lib/perf.ts` の計測用 fetch ラッパー。`PERF_DEBUG=1` のときだけ有効 |
| 同一データの重複取得 | 上のログで同じテーブル・同じ条件が1リクエスト中に何度出るかを数える |
| SQL の実行計画 | ローカル PostgreSQL に本番と同じマイグレーションを流し、**顧客1,200名 / 売上6,000件 / 監査ログ2万件** を投入して `EXPLAIN (ANALYZE, BUFFERS)` |
| 実行リージョン | レスポンスヘッダ `x-vercel-id` |

計測用ラッパーは既定では何も挟まない (`PERF_DEBUG` 未設定時は素の `fetch`)。本番の実行経路には影響しない。

```
PERF_DEBUG=1 npx next start          # サーバーログに [perf:*] が出る
```

## 2. 判明した原因

### 原因1: 実行リージョンが米国東部、DBが東京 (最大の要因)

`x-vercel-id: iad1::iad1::…` … Vercel の関数はバージニア (iad1)、Supabase は東京 (ap-northeast-1)。
**1回の問い合わせごとに太平洋を往復**しており、実測で1往復あたり約250〜280ms。
画面を1枚出すのに10回以上問い合わせるため、往復回数がそのまま秒数になっていた。

### 原因2: 同じデータを1リクエスト中に2回取っていた

`layout.tsx` と `page.tsx` がそれぞれ `requireCoach()` を呼んでおり、
Supabase クライアントも別々に作られていたため、
**認証 → `users` → `coaches` の3問い合わせが毎回2重**に走っていた (計6往復)。
さらに middleware でも認証を1回。1画面あたり7往復を身元確認だけに使っていた。

### 原因3: ADMINダッシュボードの N+1

`buildAdminCoachRows` がコーチ1名ごとに `getCoachOverview` を呼んでいた。
1名あたり8問い合わせ + 評価ルール取得。**コーチ5名で41本**、人数に比例して増える構造だった。
実測ログでは同時実行が詰まり、1問い合わせあたりの応答も270ms→1,100msに悪化していた。

### 原因4: 直列に待っていた問い合わせ

- `getCoachOverview` が評価ルールを取り終えてから残りを取り始めていた
- `loadEvaluationCustomers` が担当履歴 → 顧客 → 担当履歴 と3段直列
- `/admin/coaches` がコーチ一覧 → 担当顧客数 と2段直列

### 原因5: 一覧の並び順に索引が無い

`EXPLAIN ANALYZE` (売上6,000件 / 監査ログ2万件) で確認:

| クエリ | 改善前 | 改善後 |
|---|---|---|
| ADMIN売上一覧 (`deleted_at is null` / `sold_on desc` / 100件) | Seq Scan 6,000行 + top-Nソート **1.65ms / 119ブロック** | Index Scan **0.14ms / 102ブロック** |
| 監査ログ一覧 (`created_at desc` / 100件) | Seq Scan 20,029行 + top-Nソート **4.56ms / 390ブロック** | Index Scan **0.05ms / 5ブロック** |

件数に比例して悪化する形だったため、並び順に沿った索引を追加した (`supabase/migrations/20260101000010_performance_indexes.sql`)。

### 問題なかったもの (念のため確認した)

- 顧客・売上・担当履歴のコーチ別取得 … 既存の索引が効いている (Bitmap Index Scan)
- 成果記録の顧客別取得 … 部分索引が効いている (アプリ側も `deleted_at is null` を付けている)
- スナップショットのコーチ別取得 … `(coach_id, year_month, revision)` の一意索引で足りる
- Recharts … **そもそも import されていなかった** (依存だけ残っていたので削除。バンドルサイズは変わらない)
- CSV出力 … 全件出すのが仕様。新しい索引で並び替えが軽くなる

## 3. 行った改善

| # | 改善 | 効果 |
|---|---|---|
| 1 | Vercel の実行リージョンを東京 `hnd1` に固定 (`vercel.json`) | 1往復 250ms → 数十ms |
| 2 | Supabase クライアントとセッション取得を `cache()` で1リクエスト1回に固定 | 身元確認の往復が6→3 |
| 3 | JWT 検証を `getUser()` → `getClaims()` に変更 (非対称鍵のため JWKS でローカル検証) | Authサーバーへの往復が画面ごとに2回減る |
| 4 | ADMINダッシュボードをテーブルごと1回の一括取得へ (`getCoachOverviews`) | コーチ5名で41本 → 11本。**人数が増えても本数が増えない** |
| 5 | 直列だった問い合わせを並列化 | 待ち時間の段数を削減 |
| 6 | 一覧の並び順に索引を追加 (migration 0010) | 上表のとおり |
| 7 | middleware の対象から `/login` を除外 | ログイン画面で不要なセッション更新をしない |

**評価ロジック (`src/domain/`) は1行も変えていない。** 変更したのは取得方法・配置・索引のみ。

## 4. 結果

TTFB 中央値 (5回計測)。計測地点は日本国外のため、日本のユーザーはこれより速い。

| 画面 | 修正前 | 修正後 | 改善率 | 主原因 |
|---|---|---|---|---|
| ログイン | 1.57s | 0.35s | **-78%** | リージョン + middlewareの除外 |
| コーチ ダッシュボード | 3.06s | 0.65s | **-79%** | リージョン + 認証の二重取得解消 |
| 成果登録 | 1.76s | 0.70s | **-60%** | リージョン + 認証の二重取得解消 |
| 売上登録 | 1.50s | 0.60s | **-60%** | リージョン + 認証の二重取得解消 |
| 担当顧客一覧 | 1.37s | 0.56s | **-59%** | リージョン + 直列解消 |
| ADMIN ダッシュボード | 2.96s | 0.59s | **-80%** | N+1解消 + リージョン |
| 顧客一覧 (ADMIN) | 1.37s | 0.57s | **-58%** | リージョン |
| 売上一覧 (ADMIN) | 1.50s | 0.55s | **-63%** | リージョン + 索引 |
| コーチ一覧 (ADMIN) | 2.09s | 0.56s | **-73%** | リージョン + 直列解消 |

1リクエストあたりの Supabase 問い合わせ本数:

| 画面 | 修正前 | 修正後 |
|---|---|---|
| コーチ ダッシュボード | 18本 (うち重複6本) | 11本 (重複なし) |
| ADMIN ダッシュボード (コーチ5名) | 41本 (うち評価ルール5重複) | 11本 (重複なし) |
| 成果登録 | 8本 | 4本 |
| 売上一覧 (ADMIN) | 8本 | 4本 |

目標との対比: ダッシュボード2秒以内 → **0.6秒**。画面遷移1秒前後 → **0.4〜0.9秒**。いずれも達成。

クライアントJS: 全チャンク合計 947KB (変化なし。Recharts は元々バンドルされていなかった)。

## 5. 正確性が変わっていないことの確認

- `src/domain/` (評価ロジック) への変更なし … `git diff` で確認
- 一括取得と単体取得が**同じ評価結果**を返すことをテスト化 (`src/server/services/coachOverviewBatch.test.ts`)
  - Professional Score / 顧客成果点 / 売上集計 / 昇格判定 / 行動ルール / 報酬見込み の一致
  - 担当変更のあった顧客が「達成日時点の担当コーチ」側だけに数えられること
  - コーチ人数を増やしても問い合わせ本数が増えないこと (N+1 の再発防止)
- unit 140件 / DB整合性テスト / RLSテスト すべて通過
- 本番ブラウザ確認: 全ADMIN画面・全コーチ画面が開き、500エラー・JSエラーなし。
  未ログインでの保護画面アクセスは `/login` へ退避されること、
  ログアウト後に保護画面へ入れないこと、誤パスワードでログインできないことを確認

## 6. 今後の注意点

- **顧客一覧 (ADMIN) は全件を1ページに出している。** 数百名を超えたらページングか件数上限が必要。
  現状は絞り込みをクライアント側で行っているため、上限を入れると絞り込み結果が欠ける。
  導入するときは「サーバー側で絞り込む」形に変える必要がある。
- 監査ログ・売上一覧は100件上限のため、件数が増えても速度は変わらない。
- 月次締め (`closeMonth`) はコーチごとの直列処理のまま残している。
  月1回・夜間のバッチであり、書き込み順序と通知の正確性を優先した。
