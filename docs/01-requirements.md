# 01. 要件理解 / 論点整理

> EAGLE Coach Performance System — 設計フェーズ成果物 (実装前レビュー用)

## 1. この要件の理解

### 1-1. プロダクトの本質
このシステムは「評価制度を管理する台帳」ではなく、
**コーチが「今どこにいて、次に何をすれば上がるか」を理解し、行動を変えるためのシステム**である。

したがって設計上の優先順位は以下の順に固定する。

| 優先度 | 原則 | 具体的な設計判断 |
|---|---|---|
| 1 | コーチの入力を極小化 | コーチの日常入力は **成果登録 / 売上登録の2種類のみ**。月次報告・集計入力は一切作らない |
| 2 | 計算は全て自動 | 経過月数・評価対象判定・各種率・各種点・平均・ボーナス・昇格判定は全てシステム算出 |
| 3 | 評価の透明性 | 「何点か」だけでなく「なぜその点か」「あと何が足りないか」を必ず内訳表示 |
| 4 | 制度変更への耐性 | 閾値・配点・昇格基準は全て `evaluation_rules` にJSONで保持しversion管理。コード直書き禁止 |
| 5 | 過去評価の不変性 | 月次 `evaluation_snapshots` に「当時のルールversion + 当時の結果」を保存。制度変更で過去が書き換わらない |
| 6 | DB側での権限保証 | Supabase RLS。フロント制御は補助でしかない |

### 1-2. 評価モデルの理解

```
Professional Score (通常100点 / 最大120点)
├── 顧客成果点 (通常50点 / 最大60点)
│   ├── 長期: 完全成果率        90% → 30点 / 100% → 36点
│   └── 短期: 直近3ヶ月成果率   90% → 20点 / 100% → 24点
└── 売上点   (通常50点 / 最大60点)
    └── 売上額 → 点数 (ADMIN変更可能なマスタ)
```

- 顧客は **プログラム開始から4ヶ月経過後** に初めて顧客成果評価の対象になる (1〜3ヶ月目は入力可・評価対象外)。
- **6ヶ月プログラム終了後の達成も完全成果として遡って加算**する。未達は永久固定ではない。
- 昇格は **単月では判定しない**。3ヶ月連続 + 3ヶ月平均 + 行動ルール のAND条件。
- 四半期ボーナスも **3ヶ月平均Professional Score** で決定。単月支給判定なし。

### 1-3. 「入力2種類だけ」を成立させるために必要な前提
コーチ入力を2種類に絞る代償として、以下は **ADMIN側 or 自動** で担保する必要がある。

| 項目 | 担当 |
|---|---|
| 顧客登録・担当割当・プログラム開始日 | ADMIN |
| 定量目標の設定 → 承認 | コーチ+顧客で設定 → **ADMIN承認で確定** |
| 商品マスタ・価格・インセンティブ | ADMIN |
| 評価基準・昇格基準・ボーナス表 | ADMIN |
| 行動ルールstatus (OK/WARNING/NG) | ADMIN |
| 月次締め・四半期締め | ADMIN (ボタン1つ) + 自動ジョブ |
| 経過月数・評価対象判定・各種率・点数・平均・昇格判定 | **システム自動** |

## 2. 仕様の論点と確定した判断

Q1・Q3・Q4 はご確認いただき **推奨案で確定**。残りは推奨デフォルトで実装済み。
いずれも `evaluation_rules` の設定値なので、後から変更しても過去評価は壊れない。

### 確定サマリ

| # | 論点 | 確定した扱い |
|---|---|---|
| Q1 | 売上点のスケール | 「80/100/120点水準」はPS換算。売上サブスコアは **その1/2** (200万=40点 / 350万=50点 / 500万=60点) |
| Q2 | 月次PSの売上期間 | **当月売上 × 月次基準**。3ヶ月/年間は表示・分析用 (`scoreBasis` で切替可) |
| Q3 | 比例計算の下限 | **折れ線アンカー方式** (0%→0点 / 90%→30点 / 100%→36点) |
| Q4 | 短期成果率の母数 | **未達成者ベース** (期間開始時点で未達成の対象顧客 + 期間中に対象化した顧客) |
| Q5 | 評価対象0人 | 率=null → サブスコア=null → PS は **N/A**。連続条件はカウントせず、平均は有効月2ヶ月未満なら算定しない |
| Q6 | 解約・休会 | 自己都合解約は分母から除外 / **成果不振解約は分母に残す** / 休会は経過月数を止め分母からも除外 |
| Q7 | 達成後の悪化 | **ラチェット方式** (一度達成したら取り消さない)。達成日は「達成した記録のうち最も古い日付」 |
| Q8 | BOTH の条件 | **両方達成** (`bothGoalRule: ALL`。`ANY` に変更可) |
| Q9 | レッスン数 | コーチが **月1回だけ入力**。未入力ならレッスン報酬を除いた参考値を表示 |
| Q10 | P3/P4の上位活動要件 | **ADMINのチェックボックス承認** (件数カウント付き)。承認済みのみ昇格条件に算入 |
| Q11 | 成果の帰属 | **達成日時点の担当コーチ**。未達成は現担当 |
| Q12 | タイムゾーン | 全判定を **Asia/Tokyo** 固定。評価関数は現在時刻を内部で取得しない |

### 追加で確定した論点 (実装時に判明)

**Q13. 「開始から4ヶ月後」の解釈**

仕様7章には「開始から4ヶ月後以降」と「1〜3ヶ月目は対象外」の2つの記述があり、
前者は満4ヶ月経過 (1/1開始 → 5/1から対象)、後者は4ヶ月目に入った時点 (1/1開始 → 4/1から対象) と読める。

**採用: 満4ヶ月経過 (`minElapsedMonths: 4`)**。
根拠は仕様35章の必須テストケース。
Case 1「開始から3ヶ月 → 対象外」と Case 2「開始から4ヶ月 → 対象」の両方を満たすのは満4ヶ月経過の解釈のみ
(4ヶ月目起点だと Case 1 が成立しない)。
運用上「1ヶ月早めたい」場合は `evaluation_rules.eligibility.minElapsedMonths` を 3 に変えるだけで切り替わる。

### 各論点の詳細

#### Q1. 売上点のスケール解釈 【確定: 水準の1/2】
仕様書15章の売上基準は「2,000,000円 = 約80点水準 / 3,500,000円 = 100点水準 / 5,000,000円 = 120点水準」と
**Professional Score換算(100点満点)** で書かれている。一方16章で売上の配点は「通常50点・最大60点」。

**推奨解釈**: 「80/100/120点水準」は Professional Score 換算の水準であり、売上サブスコアはその **1/2**。

| 月次売上 | PS水準 | 売上点 (実装値) |
|---|---|---|
| 2,000,000円 | 80 | **40点** |
| 3,500,000円 | 100 | **50点** |
| 5,000,000円 | 120 | **60点** |

顧客成果側も同じ構造 (30+20=50点=100水準 / 36+24=60点=120水準) なので整合する。
→ **確定済み。** 顧客成果側 (30+20=50点=100水準 / 36+24=60点=120水準) と同じ構造になる。

#### Q2. 月次Professional Scoreに使う売上の期間
仕様には月次・3ヶ月・年間の3種類の基準がある。

**推奨**: 月次PSの売上点は **その月の売上 × 月次基準**。3ヶ月/年間基準は
ダッシュボード表示とADMIN分析にのみ使用 (昇格は3ヶ月平均PSで見るため、実質3ヶ月売上が効く)。

> 代替案: 月次PSの売上点を「直近3ヶ月売上 ÷ 3ヶ月基準」で出すと単月変動が均される。
> 大型商品(200万)の成約月に点が跳ねるのを避けたい場合はこちらが有利。ご希望あれば設定で切替可能にする。

#### Q3. 点数の比例計算の下限アンカー 【確定: 折れ線アンカー方式】
「90% → 30点、100% → 36点、比例」だけでは 90%未満の傾きが決まらない。

- 案A (2点を通る直線): `score = 60×rate − 24` → 50%で6点、40%以下で0点。**低成果に極端に厳しい**
- 案B (0%→0点 を追加した折れ線): 0%→0 / 90%→30 / 100%→36。**45%で15点**。推奨

**推奨: 案B (折れ線アンカー方式)**。アンカー配列 `[[0,0],[0.9,30],[1.0,36]]` をルールJSONに持ち、
区間線形補間 + 上限クランプ。売上点も同じ補間器を使うため、実装が1関数で済み、
将来「基準を3段階から5段階に増やす」も設定変更だけで済む。

#### Q4. 短期(直近3ヶ月)成果率の母数定義 【確定: 案C 未達成者ベース】
「直近3ヶ月で成果判定対象となった顧客」の解釈が複数ありうる。

- 案A: 分母 = 期間中に評価対象だった全顧客 / 分子 = そのうち **期間内に達成**した人
  → 過去に達成済みの顧客が分母に残り続け、**永久に率が下がる**。破綻する
- 案B: 分母 = 期間中に評価対象だった全顧客 / 分子 = **達成済み(達成日が期末以前)** の人
  → 長期成果率とほぼ同じ数字になり、短期指標の意味が薄い
- 案C (推奨): 分母 = **期間開始時点で「評価対象 かつ 未達成」だった顧客 + 期間中に新たに評価対象になった顧客**
  / 分子 = そのうち **期間中に完全達成した顧客**

**推奨: 案C**。「現在も成果を出し続けているか」という仕様の意図に最も忠実で、
過去の達成が分母に居座らず、達成済み顧客が短期率を毀損しない。

#### Q5. 評価対象0人のときの扱い
0除算は起こさない。**率 = null → サブスコア = null → Professional Score = "評価対象不足 (N/A)"** とする。

- 0点扱いにはしない (仕様36章の指示)
- N/Aの月は **昇格の「連続クリア」条件のカウントをリセットせず、加算もしない** (中断扱い)
- ボーナス算定の3ヶ月平均は、N/A月を除いた月で平均し、**有効月が2ヶ月未満なら支給判定しない**


#### Q6. 途中解約・休会顧客の分母の扱い
**推奨デフォルト**:
- `CANCELLED` (途中解約) → 解約日以降は評価分母から除外。ただし **解約理由コードを必須**にし、
  ADMINが「成果不振」を選んだ場合のみ分母に残す (逃げ得防止)
- `SUSPENDED` (休会) → 休会期間は **経過月数のカウントを停止** (4ヶ月判定が不当に早まらない)、分母からも除外
- `COMPLETED` (プログラム終了) → **分母に残す**。終了後の達成も加算されるため (仕様9章)

#### Q7. 達成後に成績が悪化した場合
**推奨: ラチェット方式**。一度 `complete_success = true` になったら、その後スコアが悪化しても取り消さない。
達成日(`achieved_at`)を確定保存。ADMINのみ監査ログ付きで手動取消可能。

#### Q8. BOTH (スコア+飛距離) の完全達成条件
仕様通り **両方達成をデフォルト** (`BOTH_RULE = ALL`)。ルールJSONで `ANY` にも切替可能にする。

#### Q9. 給与シミュレーションの「レッスン数」の取得元
`レッスン数 × ランク単価` の計算にはレッスン数が必要だが、現状どこにも入力経路がない。
コーチの入力項目を増やしたくないため、**推奨: 月1回だけ「今月のレッスン数」を入力する軽量フォーム
(ダッシュボード上の数値1つ)**。未入力ならレッスン報酬部分を非表示にし、
インセンティブ+ボーナスのみ「参考値」として表示する。
→ 将来 Google Calendar 連携で自動化できる形にしておく。

#### Q10. P3/P4 の「上位活動要件」「本人起点の事業成果」
MVPでは仕様通り **ADMINのチェックボックス承認 (件数カウント付き)** とする。
`promotion_requirement_checks` に「要件名 / 必要数 / 達成数 / 承認者 / 承認日」を持ち、
将来SNS実績・講義開催数などの自動集計に差し替えられる構造にする。

#### Q11. 成果の帰属 (担当変更時)
仕様37章通り **成果達成日時点の担当コーチ** に帰属。`customer_coach_assignments` の期間から解決する。
売上は仕様38章通り `sales.coach_id` に直接紐付け (販売者 ≠ 担当者 に対応)。

#### Q12. タイムゾーン / 月の境界
全ての日付境界は **Asia/Tokyo** で判定する。DBは `timestamptz` 保存、集計は JST の月初〜月末。
評価関数は現在時刻を内部で取得せず、必ず `asOf` を引数で受け取る (テスト可能性のため)。
